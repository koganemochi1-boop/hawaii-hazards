# v2.2 — Evacuation Routes & Shelters — Design

**Status:** Proposal — deferred. This design was originally drafted for v2.1
but the household-profile phase was prioritized instead, so it now applies to
v2.2. The design itself is unchanged and ready for sign-off when we return to
evacuation routing.

Per the project's phase process, this document proposes a content schema, an
integration approach, and one fully worked example *before* implementation. It
does not change any code yet. Once it's approved (with whatever edits you want),
the build sequence at the end becomes the implementation checklist.

Working branch (when re-activated): `v2.2-evac-routes` (off `main` at the
v2.1.0 release commit).

---

## 1. Scope

### Resolved decisions (from kickoff)

1. **Geographic scope:** all main islands — Oʻahu, Maui, Hawaiʻi, Kauaʻi,
   Molokaʻi, Lānaʻi.
2. **Shelter data:** a curated, bundled, partner-reviewable content file
   (see §3 for the GeoJSON-vs-structured-JSON reconciliation).
3. **Routing:** OpenRouteService (ORS) for walking and driving travel times
   and route geometry.
4. **Hazard-aware routing:** *flag only* — compute the normal route, then flag
   it if it crosses a relevant hazard zone. No automatic re-routing.

### Carried constraints (from the project brief)

- **Each phase keeps the app fully functional.** v2.0's report must still work
  unchanged if shelter data or ORS is unavailable. v2.1 is additive.
- **Content review gate.** Shelter and route content requires emergency-
  management partner review (HI-EMA / county civil defense) before public
  launch — this is the Phase 1 review checkpoint in the build philosophy.
  All v2.1 content ships marked `draft`.
- **Synthesis over toggling; plain language first; every risk paired with an
  action.** The shelter section is synthesis output, not a layer to toggle.

### What v2.1 adds to the report

A new **"Where to go"** section in the synthesis report, mounted after the
preparedness plan and before the map. For each hazard present at the address it
shows the nearest *appropriate* shelters, each with walking and driving travel
time, a primary and secondary route drawn on the supporting map, a flag if a
route crosses a relevant hazard zone, and plain-language evacuation guidance for
that hazard. Shelters and routes also render in the printable report.

## 3. Shelter data — `content/shelters.json`

### Format reconciliation

The kickoff answer was "curated bundled GeoJSON." This design proposes a
**structured JSON file in the same shape as `hazards.json` / `actions.json`**
rather than a raw GeoJSON `FeatureCollection`, because:

- It stays consistent with the existing `content/` + schema + validator pattern
  that v2.0 established — one mental model for content authors.
- It is far more editable by non-developers and partner reviewers: a flat list
  of shelter objects beats nested GeoJSON `geometry` / `properties` blocks.
- Shelters are points, so the only geometry is a `location: { lng, lat }` pair —
  GeoJSON's geometry envelope buys nothing here.

If you'd rather have a literal `.geojson` file (e.g. to drop straight into a GIS
tool), that's a small change — the schema below maps 1:1 onto Point features.
**This is an open decision — see §10.**

### Structure

```jsonc
{
  "$schema": "./schemas/shelters.schema.json",
  "version": "0.1.0",
  "lastReviewedBy": "draft — pending HI-EMA + county civil defense review",
  "lastReviewedDate": null,
  "notes": "Curated list of potential emergency shelters and evacuation sites across the main Hawaiian islands. These are POTENTIAL shelters — not all open for every event. The report always tells residents to confirm active shelters with their county.",
  "shelters": [
    {
      "id": "oahu_hahaione_elementary",
      "name": "Hahaʻione Elementary School",
      "island": "oahu",
      "address": "595 Pepeʻekeo St, Honolulu, HI 96825",
      "location": { "lng": -157.7065, "lat": 21.2906 },
      "shelterTypes": ["red_cross", "county_designated"],
      "attributes": ["ada_accessible", "pet_friendly"],
      "servesHazards": ["tsunami", "coastal", "flood"],
      "capacity": 1200,
      "operatedBy": "American Red Cross / City & County of Honolulu DEM",
      "activationNote": {
        "en": "Opens for coastal evacuations. Confirm it is active for your event before going — not every shelter opens for every warning."
      },
      "sources": [
        { "label": "Honolulu DEM — Emergency Shelters",
          "url": "https://www.honolulu.gov/dem/" },
        { "label": "Red Cross — Find a Shelter",
          "url": "https://www.redcross.org/get-help/disaster-relief-and-recovery-services/find-an-open-shelter.html" }
      ],
      "dataProvenance": {
        "compiledFrom": "Honolulu DEM shelter list + Red Cross Hawaiʻi",
        "lastCompiled": "2026-05-15",
        "refreshCadence": "annual + after each season's county updates"
      }
    }
  ]
}
```

### Field reference

| Field | Type | Notes |
|---|---|---|
| `id` | string `^[a-z][a-z0-9_]*$` | Stable; islands prefix keeps them readable. |
| `name` | string | Resident-facing name. |
| `island` | enum | `oahu` \| `maui` \| `hawaii` \| `kauai` \| `molokai` \| `lanai`. |
| `address` | string | Plain postal address for the card + print. |
| `location` | `{ lng, lat }` | Decimal degrees, WGS84. Validated inside Hawaiʻi bounds. |
| `shelterTypes` | enum array | `red_cross`, `county_designated`, `tsunami_vertical_evacuation`, `community`, `special_needs`. A shelter can be more than one. |
| `attributes` | enum array | `ada_accessible`, `pet_friendly`, `special_medical_needs`. Surfaced as badges. Absent = not confirmed, shown as "not listed," never as "no." |
| `servesHazards` | hazard-id array | Which hazards this shelter is an *appropriate destination* for. Must reference ids in `hazards.json`. |
| `capacity` | integer | Optional. |
| `operatedBy` | string | Optional attribution. |
| `activationNote` | localized string | The honest "not every shelter opens for every event" caveat. |
| `sources` | `{label,url}` array | ≥1, `https://` enforced — same rule as v2.0 content. |
| `dataProvenance` | object | `compiledFrom`, `lastCompiled`, `refreshCadence`. |

### `tsunami_vertical_evacuation` — a note

Some coastal areas (Waikīkī especially) have no time to reach high ground on
foot; the practical guidance is vertical evacuation to the upper floors of a
sturdy building. Those sites are modeled as shelters with
`shelterTypes: ["tsunami_vertical_evacuation"]` and `servesHazards: ["tsunami"]`,
and the selection logic (§4) treats them as valid tsunami destinations even
though they sit *inside* the tsunami zone — see the exception there.

### Honesty rule baked into the schema

Shelters open per-event. The file's `notes` and every shelter's `activationNote`
make that explicit, and the report copy will always carry "confirm active
shelters with your county." We never imply a shelter is guaranteed open.

## 4. Shelter selection logic — `js/shelters.js`

A pure-ish module mirroring the structure of `synthesis.js`. The v2.0 synthesis
engine is left alone; this runs as a second pass.

```
selectShelters({ lngLat, hazardSummaries, shelters, layerManager }) -> {
  byHazard: [
    {
      hazardId, hazard,
      shelters: [
        { shelter, distanceKm, servesHazards: Set<hazardId>, routes: null }
      ]
    }
  ],
  guidanceByHazard: { hazardId -> evacuationGuidance string }
}
```

Algorithm, per hazard with `severity !== 'none'`:

1. **Candidate filter.** Keep shelters whose `servesHazards` includes this
   hazard.
2. **Don't send people into the hazard.** Drop any shelter whose `location`
   falls inside *this hazard's* zone (point-in-polygon via
   `layerManager.getFeaturesIntersecting`, reusing the v2.0 spatial path).
   **Exception:** `tsunami_vertical_evacuation` shelters are kept even inside
   the tsunami zone — that's the whole point of vertical evacuation.
3. **Rank** remaining candidates by straight-line distance
   (`turf.distance`, cheap, no network).
4. **Keep the nearest 3** for display; the nearest **2** get real ORS routes
   (§5) to stay well inside rate limits.
5. **Dedupe across hazards.** A shelter that's appropriate for both tsunami and
   coastal flooding appears once, tagged for both — same dedupe philosophy as
   the action plan. Deduped on `shelter.id`.

If a hazard has zero candidate shelters, the section shows the honest fallback:
"No pre-identified shelter for this hazard near you — your county opens shelters
per event; here's how to find them," with the county link. No silent empties.

`guidanceByHazard` is read straight from the new `evacuationGuidance` field on
each hazard in `hazards.json` (§6).

## 5. Routing — `js/routing.js` + OpenRouteService

### Endpoint

ORS Directions v2, GET form (no request body needed for a static client):

```
https://api.openrouteservice.org/v2/directions/{profile}?api_key={KEY}&start={lng,lat}&end={lng,lat}
profile ∈ { foot-walking, driving-car }
```

Response is a GeoJSON `FeatureCollection`; we use
`features[0].geometry` (the `LineString` to draw) and
`features[0].properties.summary.{distance, duration}` (meters, seconds).

### API key handling

`js/routing-config.js`:

```js
export const ROUTING = {
  orsBase: 'https://api.openrouteservice.org/v2/directions',
  orsApiKey: '', // set locally; see README. Empty = routing degrades gracefully.
  maxRoutedSheltersPerHazard: 2,
  requestThrottleMs: 350,
};
```

The honest tradeoff: this is a static, no-build, GitHub-Pages app, so an ORS key
shipped in client JS is visible to anyone. For a **draft / partner-review phase**
that's acceptable — ORS free tier is 2,000 requests/day, 40/minute, and traffic
is low. **For public launch** the key should move behind a thin proxy (or be
swapped for a provider that supports referrer-restricted keys). This is called
out as an open decision in §10 and will be written into the README and the
v2.1 "known limitations." I will scaffold with an empty-key placeholder; the app
must work with no key (see graceful degradation).

### Routing pass

In `report-app.js`, after `selectShelters()`:

- For each hazard group, take the nearest `maxRoutedSheltersPerHazard` (2)
  shelters.
- For each, request `foot-walking` **and** `driving-car`.
- Requests run sequentially with a `requestThrottleMs` gap; results cached
  in-memory keyed by `start|end|profile` (the address is fixed per report, so a
  shelter shared across hazards is only routed once).
- **Primary route** = the ORS route. **Secondary route** = a second ORS call
  with `alternative_routes` requested, or the route to the 2nd-nearest shelter
  if no alternative is returned — exact choice finalized in implementation, but
  the UI contract is "primary + secondary."

### Graceful degradation (keeps the app functional — a hard requirement)

If `orsApiKey` is empty, ORS errors, or a request times out:

- Fall back to **straight-line distance** (already computed in §4) plus a
  rough walk/drive estimate, shown as "~est." with a clear caveat.
- No route line is drawn for that shelter; the card says "Live route
  unavailable — distance shown is straight-line."
- A `routing-unavailable` window event fires and a toast surfaces it — the same
  pattern `layers.js` already uses for live-layer fetch failures.

The report **never** fails because routing is down. This mirrors how v2.0
already treats an unavailable hazard layer.

## 6. Hazard-aware routing — flag only

Once a route `LineString` is in hand, test it against the hazard polygons
already loaded in the `LayerManager` for this address (no extra fetches):

- For each hazard present at the address, `turf.lineIntersect` /
  `turf.booleanIntersects` the route against that hazard's features.
- If it intersects, attach a flag:
  `{ hazardId, label, approxMilesInZone }` (the mileage is best-effort via
  `turf.lineSplit` / segment length; if it's awkward, we ship the flag without
  the mileage in v2.1).

Plain-language rendering, e.g.:

> ⚠ This driving route passes through the FEMA flood zone for about 0.4 mi —
> avoid it during heavy rain.

**The tsunami origin caveat.** For a tsunami evacuation, the address itself is
*inside* the zone by definition, so a naive "route touches the tsunami zone"
flag would fire on every tsunami route and mean nothing. The flag logic
therefore distinguishes:

- The **destination** must be out of the zone (already guaranteed by §4 step 2,
  except vertical-evac sites).
- We flag a route only where it **re-enters** a hazard zone after leaving it, or
  passes through a *different* hazard's zone — i.e. genuinely useful warnings,
  not a tautology. Copy for vertical-evac routes is written accordingly ("this
  route stays in the tsunami zone — that's expected; go high, not far").

Flag only. No re-routing in v2.1. If you later want "avoid where possible,"
that's a clean v2.2+ extension on top of this.

## 7. Report UI — `renderSheltersSection()`

New section, mounted by `report-app.js` after `renderActionPlan()` and before
`renderMapSection()`:

- One group per hazard (ordered by severity, same as the hazard list), each
  with the hazard's `evacuationGuidance` sentence at the top.
- Within a group, a **shelter card** per shelter: name; type badges (Red Cross /
  County / Vertical evacuation / etc.); accessibility badges (ADA, pet-friendly,
  medical) shown only when present; address; **walking time** and **driving
  time** (or the straight-line fallback); the hazard-crossing flag if any; the
  `activationNote` caveat.
- A persistent line in the section: "Shelters open per event — confirm active
  shelters with your county before you go," with the county link.
- **Map integration:** primary route drawn solid, secondary dashed, shelter
  markers added; the existing supporting-map plumbing in `report-app.js` is
  reused. Route layers respect the print stylesheet so they appear in the PDF.
- **Accessibility:** routes and times are conveyed in text on the cards, not
  only on the map — the map stays a supporting visual, consistent with the
  product principle.

No new page; this extends the existing `report.html` flow.

## 8. Validator extension — `scripts/validate-content.js`

Add a `shelters.json` pass:

- Required fields present; `id` matches the id pattern; ids unique.
- `island` in the enum; `location.lng/lat` finite and within
  `HAWAII_BOUNDS`.
- `shelterTypes` / `attributes` values in their enums; arrays non-empty where
  required.
- `servesHazards` entries all reference known hazard ids from `hazards.json`.
- `sources` non-empty and `https://`.
- Warn on `_TODO` markers and on `lastReviewedBy` still in `draft` state
  (informational, not an error — draft is expected during the phase).

Target: 0 errors before any commit that touches `content/`, same bar as v2.0.

## 9. Worked example — Waikīkī (`-157.826, 21.276`)

This traces one address end-to-end through the proposed design.

**Step 1 — v2.0 synthesis (unchanged).** `synthesize()` returns, among others:
`tsunami` → **High** ("In a tsunami evacuation zone"); `coastal` → **High**
(1% coastal flood + SLR); `flood` → **Moderate**; `wildfire` / `lava` → None.

**Step 2 — shelter selection (`selectShelters`).**
For `tsunami` (High): candidate shelters are those with `tsunami` in
`servesHazards`. Shelters physically inside the tsunami zone are dropped —
*except* `tsunami_vertical_evacuation` sites, which are kept. Say this yields,
nearest first: a vertical-evacuation high-rise 0.2 mi away, and an inland
Red Cross school shelter 1.1 mi away (outside the zone).
For `coastal` (High): overlapping candidate set; the inland school also serves
`coastal`, so it's **deduped** — shown once, tagged "Tsunami · Coastal flood."

**Step 3 — routing (`routing.js`).** For the nearest 2 tsunami shelters, ORS is
queried for `foot-walking` and `driving-car`:
vertical-evac site → walking ~5 min; inland school → walking ~24 min, driving
~7 min. The inland school is shared with `coastal`, so it's routed once and the
result reused.

**Step 4 — hazard-aware flagging.** The walking route to the inland school is
tested against the loaded hazard polygons. It starts in the tsunami zone
(expected — not flagged as a problem) and exits onto high ground; no re-entry,
so no warning. The driving route happens to clip the FEMA flood zone for ~0.3 mi
→ flag: "⚠ This driving route passes through the FEMA flood zone for ~0.3 mi."

**Step 5 — render.** The "Where to go" section shows a **Tsunami** group led by
its `evacuationGuidance` ("A tsunami warning can give only minutes — leave on
foot as soon as you hear it; do not drive."), then two shelter cards; a
**Coastal flood** group whose first card is the same inland school, tagged for
both hazards. The supporting map draws both routes (solid primary, dashed
secondary) and shelter markers. All of it prints.

**Step 6 — degraded path.** With no ORS key, every card instead shows
"~1.1 mi straight-line — live route unavailable," no route lines draw, a toast
notes routing is offline, and the rest of the report is identical. The app
stays fully functional.
